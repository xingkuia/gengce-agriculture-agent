# 耕策：桌面农业 Agent 助手技术方案

## 1. 项目定位

耕策不是模块堆叠的农业工作台，而是一个面向小型家庭农场和大型合作社的桌面农业 Agent 助手。主界面保持单一对话，用户可以从“种什么”开始，持续推进“怎么种、做了什么、结果如何、下一轮如何改进”，并把过程串成可回放、可验证、可持久化的闭环。

产品采用 Electron 无边框桌面窗口：左侧管理对话与地块，中部是唯一的任务输入和结果呈现区域，业务操作在需要时打开次级抽屉，Agent 运行轨迹只在用户主动查看时进入中性的“运行与产出”面板。浏览器入口只保留为开发与自动化验收环境。

首版以湖北为高可信区域，原因不是将系统限制在湖北，而是农业建议需要明确区分高置信规则与通用分析。湖北拥有较完整的秋冬播、水稻、油菜和小麦指导资料，适合建立第一套可评估规则集。其他地区仍可使用全国天气、公开土壤与通用作物规则完成初步分析，但界面和 Agent 产物必须降低置信度并明确说明缺失的区域证据。

产品只做软件。位置用于查询公开天气和土壤，不接传感器、农机或水肥设备。害虫图片初筛已接入百炼视觉模型；农药处方和治理效果闭环仍需要登记规则与本地标注集支持。

## 2. 用户与业务闭环

### 2.1 用户

- 小型家庭农场：劳动力有限，更关注投入可控、省工、低风险与操作提醒。
- 大型合作社：一个账号管理多个基地和多个地块，需要跨地块比较、标准化执行记录与统一复盘。

### 2.2 正确闭环

1. 用户进入预置演示账号，在左侧选择基地和地块。
2. 用户在主输入框中直接提出选种、天气、施肥或轮作问题。
3. 系统读取地块坐标、面积、轮作、灌溉、排水和最近测土数据。
4. 气象 Agent 读取天气、降水、蒸散和土壤墒情；土壤 Agent 融合公开土壤、用户测土与区域先验。
5. 选种 Agent 按稳健收益、低风险、省工易管、养地轮作四种目标分别排序候选作物。
6. 用户在同一个对话中查看差异、风险和证据，也可以用当地收购价、亩产和成本覆盖公共估算。
7. 用户自行选择候选，系统建立可执行的种植方案，并按需打开方案抽屉。
8. 用户在农事记录中登记整地、播种、施肥、灌溉、病虫监测和收获等实际作业，收获后记录结果与反馈。
9. 结果进入地块历史，反馈进入下一轮质量评估与候选改进集。

关键产品原则是“决定权留给用户”。系统可以告诉用户“不同目标下哪个候选领先”，不能用隐藏的综合分替代用户对现金流、劳力、轮作和风险的选择。

## 3. 总体架构

系统采用 Electron 宿主、Vite + React + TypeScript 渲染层和 Node 24 原生 HTTP/SSE 服务。桌面应用启动时通过 `utilityProcess.fork` 拉起本地服务并选择随机空闲端口，业务数据保存在 Node 内置 SQLite。渲染层通过受限 preload bridge 使用原生窗口能力，业务请求仍走本机 REST/SSE。

```text
Electron 无边框桌面窗口
  ├─ React 对话画布（唯一主入口）
  ├─ 业务抽屉：方案 / 记录 / 结果 / 基地 / 评估
  └─ 深色只读 Agent 执行面板
          │ preload bridge + 本机 HTTP/SSE
          ▼
     Node utilityProcess
          ├─ REST：业务数据、方案、记录、结果
          └─ SSE：Agent 运行事件
                    │
             Mastra Agent Runtime
  Agent Registry → Decision / Question Workflow
    能力快照 → 并行取证 → A2A → 校验/修复
                    │
   ┌────────────────┼────────────────┐
   │                │                │
 Tool Registry   Skill Registry   A2A Artifacts
   │
 Open-Meteo / SoilGrids / 本地规则 / 模型网关
                    │
                 SQLite
```

### 3.1 Mastra 运行时边界

Nexent 提供了编排、MCP、Skill、A2A 与评估等概念参考，但耕策最终采用 Mastra 作为完整编排运行时。Mastra 管理 Agent 与 Workflow 生命周期，耕策把农业领域能力和安全边界实现为确定性工具节点：

- Mastra Agents：八个专业 Agent 统一注册，问答按问题意图路由到对应 Agent。
- Mastra Workflow：封装选种、问答和能力快照三条可回放工作流，负责步骤顺序、并行分支、状态传递和失败收敛。
- Mastra MCPClient：真实连接远程 MCP，完成工具发现、工具级授权和调用审计；不可用时进入显式降级。
- Mastra MDocument：对导入资料做结构感知分块，检索层保留在本地 SQLite FTS5。
- 确定性工具节点：天气、土壤、选种排序、经济测算、农艺编译和 Verifier 继续使用可测试代码，模型只负责受证据约束的表达。
- Skill：系统技能不可变，个人技能支持草稿、发布、停用和四级作用域绑定。
- A2A：Agent 之间传递结构化证据包，不靠自由文本猜测上下文。
- Evaluation：固定回归集、数值复算、证据覆盖和版本门禁。

这样既让 Agent 注册、调度、流式输出和运行生命周期都经过 Mastra，又避免把农业数值规则交给不可验证的自由生成。桌面、Docker 和测试环境继续复用同一 SQLite 数据模型、SSE 协议与业务 ID。

### 3.2 能力作用域与快照

能力作用域从宽到窄为：

```text
系统内置 < 账号 < 基地 < 地块 < 当前运行临时授权
```

个人技能、MCP 服务和知识库都可以绑定到账号、基地或地块；越具体的作用域覆盖上层设置。`POST /api/runs` 可通过最多 32 条 `capabilityOverrides` 对字段级持久绑定做本轮覆盖，但必须先存在账号、基地或地块链上的绑定，不能借临时授权跨越数据边界。每次任务开始时，Mastra Workflow 和耕策业务层共同生成 `CapabilitySnapshot`：

- 记录本轮实际启用的技能、版本和指令摘要；
- 记录已授权 MCP 工具的名称和输入契约，不保存认证头或环境变量；
- 记录本轮临时启用或停用的能力引用，便于解释配置差异；
- 记录知识库作用域、命中的文档标题与片段 ID；
- 记录不可连接服务、无命中知识等降级信息；
- 用 `run_id` 唯一绑定，刷新和回放时不再读取可变配置。

能力快照写入 `capability_snapshot`，对话模型只接收快照中的个人技能规则和知识片段。知识文本被视为证据数据，不能覆盖系统规则或授予工具权限。

### 3.3 MCP 只读工具自动调用

自动工具调用与普通“工具已发现”是两个独立状态：

- 只有工具级开关已启用、服务已成功连接、当前运行快照已冻结，且 MCP 注解满足 `readOnlyHint=true`、`destructiveHint!=true` 时才进入候选。
- 规划模型只看到工具名称、描述和输入 Schema，每次最多返回两个工具。模型必须从候选 `toolId` 中选择，不能创建新工具或扩大到快照外的服务。
- 服务端再次执行 JSON Schema 基础校验，覆盖必填项、类型、枚举、范围和额外字段限制。任一调用不合格即跳过，不阻断本地天气、土壤、选种和知识检索。
- 调用开始、成功或失败都会写入 Agent 事件和 `mcp_call_log`。结果作为不可信外部证据交给回答层与 Verifier，不得覆盖系统规则。
- 写操作、破坏性操作和未声明只读语义的工具仍只能由用户在能力中心手动测试。
- 只读工具可选择 `auto`、`confirm` 或 `manual`。`confirm` 工具由规划器选出后先创建 `mcp_approval_request`，将同一运行暂停在对话内等待允许、取消或过期，不启动新的 Agent 任务。
- 批准接口只修改确认状态，不直接执行外部工具。等待中的运行随后重新读取当前工具配置与冻结快照，并再次检查账号所有权、工具启停、只读注解、执行策略和参数 Schema；任一条件变化都会拒绝执行并继续本地回答。
- 确认开始、结果、允许、取消、过期和实际调用均写入 Agent 轨迹；状态与过期时间持久化，服务重启时未决请求统一失效，避免无主运行继续等待。

## 4. Agent 设计

### 4.1 Orchestrator

负责识别任务类型、生成 DAG、并行调度天气与土壤、检查校验结果、触发局部修复并维护最多两轮修复预算。

输入为 `FarmIntent`，输出为 `MastraDecisionPlan`。Mastra Workflow 按固定 DAG 调度专业 Agent 和工具节点；Orchestrator 不做具体作物判断，也不直接生成数值结论。

### 4.2 Weather Agent

调用 Open-Meteo，读取当前温度、湿度、风速、降水、未来七日最高最低温、降水、风、参考蒸散、土壤温度和浅层土壤湿度。

输出 `WeatherEvidence`。阈值检查在代码中完成：

- 最低温不高于 2°C：低温或霜冻关注。
- 阵风不低于 13.9 m/s：施药和播种窗口风险。
- 未来三日累计降水不低于 25 mm：清沟排水风险。
- 参考蒸散不低于 4 mm：表层墒情风险。

在线请求设置短超时。失败时切换到缓存演示数据，并在 UI、事件产物和方案中保留降级标记。

### 4.3 Soil Agent

调用 SoilGrids 0–5 cm 表层属性，读取黏粒、砂粒、pH 和有机碳。用户可在“基地与地块”页面录入最近一次测土结果，手动值优先级最高。

如果 SoilGrids 超时，使用湖北区域先验，但必须：

- 在界面显示“区域先验”；
- 在经济和农艺结果中携带数据质量提示；
- 触发补救任务，把测土校准写入正式作业；
- 不允许把先验值伪装成实测值。

### 4.4 Crop Selection Agent

作物池包括水稻、油菜、小麦、玉米、大豆。水稻、油菜、小麦提供深度指导，玉米和大豆首版聚焦适宜性和经济比较。

每个作物同时拥有四个目标分：

- `profit`：稳健收益。
- `low_risk`：低风险。
- `labor_saving`：省工易管。
- `soil_health`：养地轮作。

当前播期、土壤质地、排水和轮作会对分数做可解释调整。非当前主播期会降低置信度，并明确提示“仅用于下一季比较”，不会被包装成当前可播建议。

### 4.5 Economics Agent

公开数据只提供参考区间，计算结果必须拆分为：

- 单价；
- 亩产；
- 亩均收入；
- 亩均现金成本；
- 亩均净收益；
- 按地块面积汇总的收入、成本和净收益。

用户覆盖任意一项后，结果标记为 `user-overridden`。所有计算由代码完成，LLM 只能改写表达，不得重算或新增价格。

### 4.6 Agronomy Agent

根据湖北区域播期、水肥、病虫监测和天气风险生成任务草案。每个任务包含阶段、时间窗、方法、用量或标准、依据和优先级。

方案不是一个笼统的“施肥建议”，而是可进入台账的具体作业行。例如：

- 播前开沟排水；
- 适墒精量播种；
- 三叶期间苗；
- 初花期菌核病监测；
- 低温前现场复核。

### 4.7 Verifier

Verifier 与生成 Agent 分离。首版采用确定性规则，避免同一模型自证正确：

- 数值复算：净收益必须等于收入减成本。
- 结构检查：候选方案不能没有作业任务。
- 季节检查：非当前播期不能保持高置信度。
- 证据检查：候选必须有区域或作物证据。
- 可执行性：土壤先验必须进入正式测土任务。
- 天气检查：高等级预警必须对应应急复核任务。

严重问题阻断完成；可修复问题进入 `REPAIR`，修复后重新检查。每轮运行最多两轮修复，防止无限循环。

### 4.8 Pest Vision

`POST /api/pest-assessments` 接收 FieldImage + plotId + notes，校验文件签名和 4MB 限制后调用视觉模型，以 JSON 返回候选、可见依据、相似对象区分、补拍要求和监测措施。结构校验失败、模型超时或无权限均显示可重试错误，不伪造结果。

`GET /api/pest-assessments?plotId=...` 返回该地块最近 10 条记录。SQLite 只存结构化结论、时间、模型、耗时和 token 用量，不存原图。没有本地标注集的准确率结论，不提供农药品名、剂量和混配处方。

Mastra 按 summary / vision 角色选择模型，统一管理 Agent 并发、排队、超时和临时错误重试；病虫害视觉与 MCP 只读工具规划也通过已注册的 Mastra Agent 执行。核心数值与季节规则仍由确定性工具和独立 Verifier 校验。

## 5. A2A 与事件模型

Agent 之间传递的不是非结构化聊天，而是带类型的产物：

- `WeatherEvidence`
- `SoilEvidence`
- `EvidenceBundle`
- `CandidateSet`
- `EconomicEstimate`
- `PlantingPlanDraft[]`
- `VerificationReport`
- `RepairRequest`
- `RecommendationSet`
- `GroundedAnswer`

`agent_event` 表保存运行 ID、顺序、Agent、事件类型、状态、说明、结构化 payload 和时间。前端通过 SSE 接收事件，刷新后可从 SQLite 重新回放。

事件类型包括：

- `plan`：任务拆解；
- `tool`：工具调用；
- `a2a`：结构化产物交接；
- `verify`：校验；
- `repair`：修复；
- `answer`：专家问答；
- `system`：完成或失败。

## 6. 数据源与可信度

### 6.1 天气

Open-Meteo 提供位置相关天气和蒸散。在线状态与缓存状态在系统中明确区分。

### 6.2 土壤

SoilGrids 提供公开表层属性，但不能替代测土配方。公开请求超时是正常工程场景，因此系统必须有区域先验与显式降级。

### 6.3 农艺规则

首版使用湖北省农业农村厅公开指导材料作为规则依据，包括：

- 2025 年农业主推技术指南；
- 2024 年小麦、马铃薯秋冬播指导意见；
- 2024–2025 年油菜生产技术指导意见；
- 小麦、油菜田管指导意见；
- 水稻、玉米防灾减灾指导意见。

规则在代码中结构化保存，不与 UI 文案混合。后续每个区域应拥有独立规则版本、生效时间和评估集。

### 6.4 经济数据

价格、亩产和成本来自公开资料形成的参考区间。页面必须显示“公开估算、非实时收购报价、可被用户覆盖”。不得把演示区间说成真实平台实时行情。

## 7. 模型网关

模型通过服务端 OpenAI 兼容接口调用。当前支持：

- DeepSeek；
- 阿里百炼 / 千问兼容模式；
- Mock 确定性模式。

环境变量只存在服务端 `.env` 或 Docker 环境。前端无法读取密钥。

模型角色是“受约束表达层”：输入确定性候选、天气、土壤与经济结果，输出短结论和下一步行动。模型失败或未配置时自动回退，不阻断业务。数值、季节、证据和安全检查不交给模型自由发挥。

若要调用百炼中的其他模型，只需设置对应的 `MODEL_BASE_URL` 和 `MODEL_NAME`，无需修改 Agent 业务代码。若控制台提供工作空间专属地址，应使用其 `.../compatible-mode/v1` 地址；公共兼容地址只作为通用示例。生产环境建议为表达层和校验层配置不同模型族，以降低同源错误。

## 8. 数据模型

主要表：

| 表 | 用途 |
| --- | --- |
| `account` | 账号与套餐 |
| `farm` | 基地和坐标 |
| `plot` | 地块、面积、土壤、灌溉、排水和轮作 |
| `plot_context` | 最近天气与土壤快照 |
| `task_run` | 一次 Agent 运行 |
| `agent_event` | 可回放执行事件 |
| `recommendation` | 候选、分数、经济、证据和方案草案 |
| `planting_plan` | 用户选择的正式方案 |
| `operation_record` | 计划与实际行动 |
| `outcome_record` | 实际产量、品质、收入、成本和利润 |
| `feedback` | 用户评分与文字反馈 |
| `agent_version` | Agent 版本和变更说明 |
| `evaluation_run` | 固定回归集评估结果 |

SQLite 适合本地 Docker 和比赛演示。生产扩展到多人多租户时，可迁移到 PostgreSQL，但业务 ID、事件顺序和 JSON 契约无需改变。

## 9. 评估与自进化

自进化不是让 Agent 在线自动改自己的 Prompt。正确流程是：

1. 收集运行失败、低评分和实际结果偏差。
2. 形成候选改进，例如新增规则、调整工具阈值或增加任务。
3. 在固定回归集上回放。
4. 通过质量门禁后才发布新版本。
5. 保留版本号和回滚能力。

当前回归集覆盖：

- 结构化输出；
- 数值复算；
- 不适播保护；
- 证据覆盖；
- 修复循环。

建议后续扩展的案例：

- 湖北不同纬度与海拔的播期差异；
- 连续阴雨与渍害；
- 极端低温；
- 轮作冲突；
- 用户覆盖极端价格与成本；
- 土壤数据完全缺失；
- 模型超时和返回越界；
- 同一问题在不同目标下的排序差异；
- 实际结果显著低于估算。

## 10. 安全与治理

- 密钥只存在服务端环境变量。
- 所有 SQL 使用参数绑定。
- API 请求体限制为 1 MB。
- 前端输出由 React 转义。
- 图片识别阶段需要单独的人体安全、农药合规与个人数据治理。
- 用户田间数据默认用于自身决策，不默认进入模型训练。
- 结果页面必须避免保证产量、保证价格或把估算说成事实。

## 11. 部署与扩展

主交付是 Windows x64 桌面应用。开发时运行 `pnpm desktop`，打包时运行 `pnpm desktop:package`，产物位于 `release/Gengce-win32-x64/`。应用内嵌本地 Agent 服务，不要求用户另外启动网页或 API 进程。模型配置从项目 `.env` 或 `%APPDATA%\耕策\.env` 读取，环境文件不会进入 ASAR。

同时保留 Docker Compose 作为可复现的本地评测环境：

```bash
cp .env.example .env
docker compose up --build
```

数据保存在具名卷。Docker 入口与桌面应用共享同一套 Node 服务、数据库结构和 Agent 事件协议，适合自动验收与排障，但浏览器页面不是主要产品形态。正式多人部署时再增加认证、对象存储、备份、审计和 PostgreSQL。

全国扩展的顺序应为：

1. 全国基础天气、土壤和作物适宜性；
2. 按省份建立规则包和来源；
3. 按生态区建立固定评估案例；
4. 与当地农技资料、价格口径和品种审定目录校准；
5. 没有区域证据时主动降低置信度，而不是用湖北规则强行覆盖全国。

## 12. 竞赛差异化

本项目最值得展示的不是“有很多 Agent 图标”，而是以下四点：

1. Agent 之间通过结构化 A2A 产物协作，且所有事件可回放。
2. 数值和安全由独立校验器和代码门禁控制，生成与验证分离。
3. 一次修复循环在演示中真实发生：土壤先验触发新增测土复核任务。
4. 业务结果不止步于建议，而是进入方案、农事、结果和反馈的持久化闭环。
